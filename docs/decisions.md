# 裁决记录

本仓是 2026-09-30 重启后的新仓,不带旧仓历史。以下几条裁决在旧仓(现 `VidRoom-legacy`,私有归档)里仍然成立,迁过来存档;旧仓的其余裁决(机器实况、待拍板项)本轮不迁,已在新的合同里重新处理。

## D-001 命名:PilotLab → VidRoom(2026-08-20,Dav 裁,迁自旧仓)

产品名与仓名统一为 `VidRoom`(仓名 = 产品名)。原名 `AI Studio Pilot` 把 Google **AI Studio** 与 **Copilot** 两个商标词拼在一起,创业项目须绕开。

2026-09-30 重启时复核过一次同名风险(未查透),沿用这个名字。

## D-002 显存策略:不为生成停用户桌面(2026-08-21,Dav 裁,迁自旧仓)

按用户机器的实际可用显存分档,不替用户关掉正在跑的其它程序(浏览器、游戏、串流等)去腾显存。

## D-004 模型体积不可信,用前必须用官方 API 复核(2026-08-20 实测,迁自旧仓)

第三方文档或社区帖子里写的模型体积经常是错的(旧仓踩过一次:文档称某模型约 66GiB,Hugging Face API 实测其大文件合计 187GiB)。

**规矩**:凡是模型体积、显存/内存预算的数字,用前先用 Hugging Face API(`tree/main?recursive=1` 的 `lfs.size`)或对应平台的官方 API 复核一遍,不要直接信文档或帖子。

## D-005 调用方是 agent,不是人(2026-08-21,Dav 本人澄清,迁自旧仓)

VidRoom 的默认使用方式是用户跟内置 agent(LLM)聊天,由 agent 写生成参数、选工作流。由此定下:

1. 结构化任务与生成提示词由 agent 写,不做面向人类的中文关键词编译层。
2. agent 能看到全部技术细节(显存估算、成片路径、实际参数);面向普通用户的界面默认隐藏这些技术视图,但不能因为"藏起来"就连 agent 自己也拿不到 —— 它需要这些信息才能做出正确的降档决定。

## 实测基准(迁自旧仓,标注机器与操作系统)

以下数据来自旧仓在**旧开发机(Linux,RTX 4060 Ti 16GB)**上的实测,不是 Windows 数据,3090 机的数字要重新测:

- Wan 2.2 TI2V-5B,1280×704、121 帧、20 步、开 `--fast-disk`:耗时 704.2 秒,显存峰值 12.85 GiB,内存峰值 14.12 GiB。
- 内存开销近似随「分辨率 × 帧数」的总像素量线性增长(旧仓拟合:内存 ≈ 1.1 GiB + 0.12 GiB × 像素量(Mpx·帧),仅供参考,不是精确公式)。

## D-006 形态:独立 app → dsh 插件(2026-10-04,Dav 裁)

本仓的形态从「独立 Windows app(Node Host + React 网页 + Electron 壳)」改成 **DeepSeek Harness 的一个插件**
(`apps/dsh-vidroom`):桌面壳、ComfyUI 起停、聊天会话全部交给宿主,本仓只做「本地 H3 出片 + 工作流库 + 中文」那一小块。

三个 app 包与它那套 Playwright e2e 已从 main 删掉,留档在 tag `legacy-app-final`。裁决背景与风险边界见私有仓记录,不在此处复述。
